# MICRO / PLANET · Babylon.js + C++

Самостоятельная копия WASD Playground. Клиент работает в браузере на Babylon.js 8.56.2, сервер — C++17, Drogon и libdatachannel 0.23.2. WebSocket используется для сигналинга, WebRTC — для позиций игроков, ping и подтверждений состояния общей комнаты. Node.js, npm и Godot для сборки и запуска не нужны. Python нужен только для необязательного локального распознавания речи у профессоров.

Проект можно перенести отдельно от исходного приложения; Node.js для его запуска не требуется. При переносе на другой путь или компьютер удалите каталог `build/` и выполните сборку заново; CMake хранит абсолютные пути в кэше. Все модели, данные и Babylon.js находятся внутри; CDN и исходные файлы Godot при запуске не используются.

## Запуск

На macOS нужны CMake, C++ compiler и Drogon:

```bash
brew install cmake drogon
cd soloapp_app
./scripts/build.sh
./scripts/start.sh
```

Откройте <http://127.0.0.1:3000>. Один C++-процесс обслуживает страницу и сигналинг `/signal`. Для мультиплеера войдите под разными аккаунтами: владелец создаёт сервер, остальные вступают и ждут запуска. Вкладки одного браузерного профиля используют сохранённую сессию; для другого аккаунта удобно отдельное приватное окно. Другой порт: `./scripts/start.sh 3001`. Остановка — Ctrl+C.

На Linux установите CMake 3.20+, C++17 compiler, Drogon с development-заголовками, OpenSSL и SQLite3. Нестандартный путь к Drogon передаётся как `./scripts/build.sh -DCMAKE_PREFIX_PATH=/path/to/prefix`. libdatachannel и его зависимости CMake загружает при первой сборке, если отсутствует локальный кэш `.cache/datachannel-src`. Последующие сборки используют локальные исходники.

Параллелизм сборки: `BUILD_JOBS=2 ./scripts/build.sh`. Если бинарника ещё нет, `start.sh` запускает сборку автоматически. Существующий бинарник после изменений C++ обновляйте через `build.sh`.

## Вход и авторизация

Мир загружается сразу: можно гулять локально без аккаунта и без WebSocket/WebRTC. Вход обязателен только для общего мира. Почта и пароль вводятся на 3D-панели внутри сцены; одна и та же панель работает мышью в браузере и лучом контроллера в VR. Поля поддерживают физическую клавиатуру, вставку и виртуальную клавиатуру с регистром, символами и удалением. Пароль скрыт точками. По умолчанию панель создаёт аккаунт; кнопка «Уже есть аккаунт? Войти» переключает на вход. Пароль — от 8 до 128 байт. Почта служит идентификатором аккаунта; подтверждение письмом и восстановление пароля пока не реализованы.

C++ сервис предоставляет:

| Метод | Адрес | Данные / авторизация |
| --- | --- | --- |
| POST | `/api/auth/register` | JSON `{ "email": "you@example.com", "password": "…" }` |
| POST | `/api/auth/login` | Тот же JSON |
| GET | `/api/auth/me` | `Authorization: Bearer <token>` |
| POST | `/api/auth/logout` | `Authorization: Bearer <token>` |

Регистрация и вход возвращают `token`, `token_type`, `expires_at` (Unix seconds) и `user`. Токен действует 24 часа и сохраняется в `localStorage` под ключом `microplanet.auth.v1` вместе с исходным сроком действия и почтой. Пароль не сохраняется. После перезагрузки сессия восстанавливается автоматически; C++ сервер повторно проверяет токен при авторизации WebSocket до начала синхронизации. Выход, истечение срока и отказ сервера удаляют соответствующий сохранённый токен. Если хранилище браузера недоступно, вход работает в текущей вкладке с уведомлением о невозможности сохранения. Хранилище отдельное для каждого origin: `localhost`, `127.0.0.1` и разные порты не разделяют сессию. Первое сообщение WebSocket — `{ "type": "auth", "token": "…", "server_id": 1 }`; оно отправляется после запуска выбранной комнаты. Сервер разрешает SDP/ICE и выдаёт `welcome` только после проверки токена. WebRTC-соединение с сервером привязано к этой авторизованной сессии. Истечение или отзыв токена закрывает её WebSocket и WebRTC; клиент снова показывает 3D-панель входа, сохраняя возможность локальной прогулки. Токен не передаётся другим игрокам или в URL. «Выйти» отзывает текущий токен, другие сессии аккаунта остаются активными.

Аккаунты сохраняются в `runtime/auth.sqlite3`, вне публичных файлов. Пароли хешируются через scrypt с индивидуальной солью; для токенов сохраняются только SHA-256 хеши. Файл БД доступен владельцу, каталог исключён из Git. Путь меняется через `--auth-db=/path/to/auth.sqlite3`. Обработка паролей выполняется отдельно от цикла мира, очередь и частота запросов ограничены. Для доступа за пределами localhost используйте HTTPS/WSS.

После обновления перезапустите C++ сервер и обновите страницу с обходом кэша. Старый сервер не имеет ручек авторизации.

## Что перенесено

- Сферическая микропланета радиусом около 36 м, исходный рельеф 128 × 256, четыре озера и карты дна.
- Исходные 43 берёзы: стволы, ветки и 37 840 отдельных зубчатых листьев; 18 000 пучков изогнутой травы. Геометрия и размещение экспортированы из исходного генератора, листья и трава используют GPU instances.
- 48 рыб с исходной геометрией, размерами, цветами и фазами хвостов. C++-симуляция скопирована без изменения алгоритма: 12 рыб в каждом озере, реакция на игрока до 4 м, движение между дном и поверхностью, успокоение после ухода игрока.
- WASD, мышь, местная вертикаль и радиальная гравитация, столкновения со стволами, замедление в воде. Первый и третий вид, сокращение плеча камеры у препятствий, обзор всей планеты.
- Вода с глубиной, прозрачностью, бликами, береговой пеной и расходящимися волнами от своего и удалённых игроков. Подводный оттенок, каустики на дне, колыхание растительности.
- Синтезируемые в браузере ветер, шелест, береговая вода, шаги и всплески; плавные переходы и приглушение под водой.
- До 8 игроков, обновления позиций между peers 20 раз в секунду, интерполяция, RTT, ID и расстояния. C++ передаёт состояние комнаты и позиции её участников по авторизованному WebRTC 10 раз в секунду: игроки видят друг друга и при недоступности прямого peer-соединения. Отсутствие пакетов 10 секунд перезапускает канал. Рыбы и их исходная симуляция сохранены в проекте, но в белой комнате не запускаются.
- WebXR: местная вертикаль сферы, движение левым стиком, поворот правым на 30°, кнопка A для панели, уменьшенная плотность травы, восстановление камеры после выхода.

Материалы переписаны на GLSL для Babylon.js. Это перенос геометрии и поведения, а не побитовое воспроизведение изображения Godot: освещение и материалы отличаются; динамические тени реализованы локальной картой глубины вокруг камеры и отключаются в VR. Коллизия поверхности использует интерполяцию сохранённой сетки высот; отличие от аналитического генератора в проверенных точках озёр — до 5,3 см. Листва, трава и модели рыб сохраняют исходные параметры.

## Управление

В локальной прогулке у каждого из четырёх озёр стоит профессор Эйнштейн
(модель klava88, CC BY 4.0). Он размещён на сухом берегу, вне стволов деревьев,
с учётом местной вертикали планеты. При приближении на 5,5 м профессор плавно
поворачивается к игроку и приветствует его на 3D-табличке. После удаления
на 6,5 м возвращается в ожидание; разница порогов предотвращает мерцание реакции.
В белой сетевой комнате профессора скрыты. Это статическая модель без скелета:
реакция состоит из поворота и приветствия. Проверка модели: `/professor-checks.html`.

### Речь у профессоров (локальная прогулка)

При включённом микрофоне голосового чата профессор автоматически расшифровывает
вашу речь, когда вы рядом. Отдельных кнопок и клавиш записи нет: используется
обычное управление микрофоном чата (**N** / кнопка «Микрофон», **X** в VR).
Общий микрофон доступен также в локальной прогулке без аккаунта. Его выключение
завершает расшифровку и отправляет последний короткий фрагмент.
Профессор использует тот же `MediaStream`, без второго запроса разрешения;
не меняет обработчики аудиодорожек и не останавливает их. Ошибка Whisper не
отключает голосовой чат. Нужен localhost либо HTTPS. В белой сетевой комнате
расшифровка отключена.

Для каждого посещения озера создаётся отдельная дорожка текущего участника;
при смене озера её остаток завершается, следующий буфер начинается пустым.
В локальной прогулке участник один: удалённые голоса здесь не подключаются.
Вне зоны профессоров микрофон остаётся включённым до остановки, но аудио
не буферизуется и не отправляется на распознавание. При скрытии вкладки
расшифровка приостанавливается и возобновляется при возвращении, если микрофон
чата всё ещё включён. При выходе из аккаунта, входе в сетевую комнату и перезагрузке
исчезает также текст.

Аудио существует только в оперативной памяти браузера и worker, без аудиофайлов
и БД. Текст хранится в памяти вкладки отдельно по озёрам и отображается рядом
с соответствующим профессором (последние строки; история ограничена).
Из микрофона передаётся mono PCM16 16 kHz: окна 8 секунд, шаг 6 секунд,
перекрытие 2 секунды. Слова объединяются по временным меткам, без повторного
вывода перекрытия; последние слова могут уточняться следующим окном.
Первая расшифровка появляется примерно через 8 секунд плюс время inference;
выключение микрофона чата отправляет короткий остаток. Очереди ограничены: если Whisper
не успевает, запись останавливается с сообщением.

На **macOS Apple Silicon** используется `mlx-whisper==0.4.3` и
`mlx-community/whisper-large-v3-turbo-4bit` (зафиксированная ревизия).
Один раз установите `uv`, Python 3.12 и Hugging Face CLI `hf`, затем:

```bash
./scripts/setup-whisper.sh   # зависимости и веса в .cache; требует интернет
./scripts/start-whisper.sh   # оставить отдельным процессом
./scripts/start.sh          # в другом терминале, после build.sh
```

Worker выполняет inference локально с `HF_HUB_OFFLINE=1`, слушает только
`127.0.0.1:8178`, не сохраняет и не логирует разговоры. C++ проксирует
`GET /api/professors/health` и `POST /api/professors/transcribe` в этот фиксированный
loopback endpoint; проверяет origin, размер и ограничивает параллелизм. Запросы
не используют общую историю Whisper или previous-text prompt. Worker должен
работать на компьютере C++ сервера; с VR-шлема аудио попадёт на этот компьютер.
Другой локальный каталог MLX-весов задаётся через `WHISPER_MODEL` (должен содержать
`config.json` и `weights.safetensors`), порт через `WHISPER_PORT` у worker и
`--whisper-port=` у C++ сервера. Без worker прогулка и голосовой чат доступны,
профессор покажет инструкцию запуска. После запуска worker выключите и включите
общий микрофон для повтора подключения. Linux/Windows backend распознавания пока не добавлен.

Проверки:

```bash
node scripts/speech-test.mjs
python3 scripts/whisper_service_test.py
# macOS: нужен ffmpeg, работающие приложение и Whisper; только синтетическая речь
python3 scripts/whisper-smoke.py --url http://127.0.0.1:3000
```

Страница `/transcription-checks.html` проверяет настоящий AudioWorklet на
синтетическом MediaStream голосового чата, единственный запрос микрофона,
разделение озёр, остановку/короткий хвост при выключении чата, отказ разрешения,
поздний ответ worker и сохранение работы чата при ошибке Whisper.
Распознаватель на этой тестовой странице
заменён заглушкой; реальный Whisper проверяется `whisper-smoke.py`, который
удаляет временные синтетические WAV/AIFF после выполнения. Физический микрофон
и VR-шлем проверяются отдельно.

Описание используемого backend: [MLX Whisper](https://github.com/ml-explore/mlx-examples/tree/main/whisper).

После регистрации открывается выбор из трёх локальных аватаров: «Атлет» и «Атлетка»
(Quaternius Universal Base Characters, Superhero, CC0), а также «Очако Урарака»
(Padalab, CC BY-NC-SA 4.0). Выбор сохраняется в
`localStorage` под ключом `microplanet.avatar.v1` и восстанавливается при загрузке.
Это настройка браузера для текущего origin, общая для аккаунтов на этом устройстве.
При недоступном хранилище модель меняется на время текущей вкладки с уведомлением.

Изменить выбор можно через «⚙ Настройки» на компьютере или 3D-шестерёнку в VR
(луч контроллера + триггер). Кнопка B закрывает настройки или открывает список серверов после входа.
Авторизация и настройки используют один `AccountPanel`: общую 3D-поверхность,
отрисовку, обработку мыши и XR-лучей. Пока настройки открыты, движение приостановлено;
«Закрыть», Esc или B возвращают управление. Модель и сохранение меняются только
после успешной загрузки; при ошибке можно повторить попытку, прежний аватар остаётся.

Аватар виден в третьем лице (`V`) и обзоре планеты (`Tab`). Модели Quaternius
имеют скелет из 65 костей, процедурную походку и наклон головы по взгляду.
Урарака — статическая модель без скелета и анимаций: перемещается с игроком,
сохраняя исходную позу. Из предоставленного GLB выделена центральная фигура;
две боковые позы и декоративный фон удалены. Скрипт подготовки:
`python3 scripts/prepare-uraraka.py SOURCE.glb public/assets/avatar/uraraka-ochako.glb`.
Автор, источник, лицензия и изменения указаны отдельно в
`public/assets/avatar/URARAKA-LICENSE.txt`; лицензия CC0 Quaternius на неё не распространяется.
В первом лице и WebXR тело скрыто, как и прежняя капсула; отслеживание рук и IK
в этой версии не добавлены. Удалённые игроки используют прежнее представление.
Модель загружается независимо от входа в аккаунт. Пока она загружается или если
загрузка не удалась, остаётся капсула, и прогулка продолжает работать.

`public/assets/avatar/player.glb` и `player-female.glb` содержат геометрию, скелет и все текстуры
(до 1024 px), поэтому не требует CDN. glTF-загрузчик поставляется локально и
совпадает с версией движка 8.56.2. Лицензия и происхождение записаны в
`public/assets/avatar/LICENSE.txt` и `ASSET-PROVENANCE.json`.

## Серверы и комната ожидания

После входа 3D-панель показывает серверы из C++ API. «Создать сервер» делает текущего пользователя владельцем и первым участником. Другие пользователи выбирают «Вступить» и видят состав комнаты. Вместимость — 8 участников; один аккаунт может состоять только в одном сервере. Одновременно допускается до 8 WebSocket-подключений к одной комнате.

Только владелец может нажать «Запустить мир». Комната проходит состояния `waiting` → `loading` → `countdown` → `running`. После команды запуска каждый клиент готовит сцену и материалы новой карты, затем подтверждает готовность через HTTP. Когда все готовы, C++ назначает общий момент перехода через 3000 мс. У всех появляется модальная 3D-панель с отсчётом 3–2–1; она видна также в VR и блокирует движение и действия геймпада. Сигнализация и WebRTC разрешаются только после окончания отсчёта.

Список, состав и состояние перехода обновляются HTTP-запросами раз в 250 мс. «Серверы», Esc после прогулки или B в VR возвращают к панели. Можно выйти из комнаты; выход владельца или «Закрыть свой сервер» закрывает её для всех. После начала загрузки новые участники не принимаются. Если один из участников не закончил загрузку, комната продолжает ждать его; владелец может закрыть сервер и создать новый.

Серверы, владельцы и участники хранятся в таблицах `game_servers` и `game_members` в той же SQLite БД, что и аккаунты. Клиент не хранит список серверов в localStorage. Перезагрузка страницы восстанавливает членство через API. Перезапуск C++ сохраняет комнаты, но переводит их в ожидание: состояние физики не сохраняется, нужен новый запуск владельцем. Выход из аккаунта не удаляет комнату; для этого используйте «Закрыть свой сервер». До 64 комнат на экземпляр сервиса.

Все ручки требуют `Authorization: Bearer <token>`. Владелец и участник определяются сервером из токена.

| Метод | Ручка | Действие |
| --- | --- | --- |
| GET | `/api/servers` | Список, `user_id` и текущая комната `current` |
| POST | `/api/servers` | Создать; необязательный JSON `{ "name": "Моя планета" }` |
| GET | `/api/servers/{id}` | Комната, владелец, участники и готовность |
| POST | `/api/servers/{id}/join` | Вступить в ожидающую комнату |
| POST | `/api/servers/{id}/leave` | Выйти; владелец закрывает комнату |
| POST | `/api/servers/{id}/start` | Начать подготовку мира, только владелец |
| POST | `/api/servers/{id}/ready` | Подтвердить готовность сцены |
| DELETE | `/api/servers/{id}` | Закрыть комнату, только владелец |

В первом сообщении `/signal` вместе с токеном передаётся `server_id`. C++ проверяет членство и состояние комнаты. У каждой комнаты отдельный состав игроков; список peers, SDP/ICE и пакеты позиций не пересекаются между серверами. Удаление комнаты или выход участника закрывает соответствующее соединение с миром.

## Переход в белую комнату

Каждый запущенный сервер открывает отдельную карту `white-room`: помещение 24 × 24 м с белыми стенами, потолком высотой 6 м и плоским полом. Планета, вода, растительность и звуки природы скрываются. Восемь раздельных точек спавна отмечены на полу; слот назначает C++ при вступлении и сохраняет в SQLite. Действуют столкновения со стенами, вид от первого и третьего лица, управление DualSense и WebXR.

API возвращает `server_time_ms`, `map`, общий `starts_at_ms` и `members[].spawn_slot`. Клиент рассчитывает отсчёт с поправкой на серверные часы; при потере связи ждёт подтверждения запуска. Повторные `start` / `ready` не продлевают таймер. При перезагрузке в запущенном мире игрок снова появляется на своём спавне без нового отсчёта. Выход из комнаты, её закрытие владельцем или выход из аккаунта возвращает на прежнее место локальной планеты. Старая БД обновляется автоматически без удаления аккаунтов, серверов и участников.

Проверен переход двух независимых браузерных сессий: модалка 3–2–1, общий дедлайн, разные спавны, видимость игроков по WebRTC, восстановление после перезагрузки и возврат на планету. Физический VR-шлем для этой проверки не использовался.

## DualSense / PS5

Подключите контроллер к компьютеру по USB или Bluetooth, откройте игру и нажмите любую кнопку. При обнаружении стандартного геймпада появится строка подсказок. Ходьба и обзор работают без захвата мыши; при открытой 3D-панели левый стик переключает элементы меню.

| Кнопка / стик | Действие |
| --- | --- |
| Левый стик | Ходьба; в меню — выбор элемента |
| Правый стик | Обзор; в VR — поворот на 30° |
| Крестовина | Выбор элемента 3D-панели |
| ✕ | Подтвердить / нажать клавишу виртуальной клавиатуры |
| ○ | Закрыть панель и продолжить прогулку; выйти из обзора планеты |
| □ / Options | Открыть / закрыть вход или список серверов |
| L1 / R1 | Предыдущий / следующий элемент панели |
| △ | Переключить первое / третье лицо вне VR |
| R3 | Обзор всей планеты / вернуться вне VR |

Выбранный элемент выделяется светлой рамкой. С геймпада доступны ввод почты и пароля, вход, создание и выбор сервера, запуск мира владельцем и выход. Удержание ✕ не повторяет отправку формы или действие после смены панели. Небольшое отклонение стиков игнорируется; отключение контроллера, потеря фокуса или скрытие VR-сессии останавливают управление. После возвращения отпустите кнопки и стики, чтобы продолжить. Контроллеры WebXR обрабатываются отдельно.

Проверено в Chrome с имитацией стандартного Gamepad API, включая 3D-клавиатуру и полный путь до C++ / WebRTC. Физический DualSense и его работа в шлеме требуют отдельной проверки. Раскладка соответствует [стандартному отображению Gamepad API](https://w3c.github.io/gamepad/#remapping).

## Чёткость изображения

По умолчанию включена высокая графика: рендер учитывает плотность пикселей экрана (до 2×, с ограничением 6 млн пикселей), MSAA до 4× и мягкое повышение резкости. На обычном дисплее используется дополнительное разрешение 1,25×. Лёгкий режим снижает разрешение и использует FXAA. Сглаживание применяется к обеим обычным камерам. Текстура 3D-формы имеет разрешение 2048 × 2240, mipmaps и анизотропную фильтрацию.

У VR отдельный режим, выбираемый перед входом в шлем: «плавно» использует штатное разрешение WebXR и 6000 пучков травы; «детально» увеличивает размер framebuffer в 1,25 раза по каждой стороне и оставляет 12000 пучков. Настольные постэффекты к XR-камерам не подключены. Итоговую плавность и чёткость нужно проверить на конкретном шлеме.

## Сеть и Quest

Сервер по умолчанию слушает loopback. Каждый игровой сервер из списка — отдельная комната внутри C++ процесса, со встроенным loopback TURN для браузеров на этом компьютере. Параметр `?signal=` допускает только тот же хост и порт, что и страница, с WS для HTTP или WSS для HTTPS; это исключает отправку токена стороннему серверу. Babylon-клиенты используют собственный JSON-протокол в peer DataChannels, поэтому подключайте их к этой отдельной комнате, не смешивая с Godot RPC-клиентами оригинала.

WebXR требует защищённого контекста: localhost или HTTPS. Для Quest по USB:

```bash
adb reverse tcp:3000 tcp:3000
```

В Meta Quest Browser откройте `http://localhost:3000` и нажмите «Войти в VR · Quest». ADB переносит HTTP/WebSocket, но не UDP WebRTC: для мультиплеера шлем и компьютер должны также иметь прямое сетевое соединение. Вход в общий мир требует доступного сервера. До входа, после выхода и при истечении токена локальная прогулка продолжается; удалённые игроки отключены. Статические файлы мира загружаются по HTTP, игровая синхронизация до входа отсутствует. Физическое перемещение головы не проверяет коллизии.

## Лабораторная веранда

Рядом со стартовой точкой находится отдельная деревянная веранда с открытым навесом, пандусом, ограждениями и двумя рабочими столами. Вход обращён к старту; участок автоматически выбирается на суше, вне деревьев и профессоров. По настилу можно ходить с клавиатуры, геймпада и через VR-перемещение. Пол, пандус, столы и ограждения участвуют в коллизиях. В белой комнате веранда скрыта.

На столах стоят две открытые пробирки: синий образец A (40 мл) и янтарный образец B (30 мл). Захват и смешивание пока не реализованы. Для их добавления каждый сосуд в `Laboratory.vessels` уже имеет отдельный `root`, зону выбора `pickMesh` с `metadata.vesselId`, ёмкость `capacityMl`, массив `contents` и исходную позу `restPosition` / `restRotation`. Стекло, жидкость и зона выбора принадлежат сосуду; подставка остаётся на столе. Будущий VR-захват можно подключить к корню сосуда, а изменение состава — к его данным, не разбирая геометрию веранды. Все объекты локальные; сетевой синхронизации лаборатории пока нет.

Геометрия создана процедурно в `public/client/laboratory.js`, выбор участка — в `public/client/lab-site.js`. Проверка `/laboratory-checks.html` проверяет размещение, проход по пандусу обычным и VR-перемещением, коллизии, выбор обеих пробирок лучом, независимость сосудов и скрытие в другом мире. VR-перемещение в проверке синтетическое, без физического шлема.

Веранда создаётся при первом приближении на 10 м и скрывается после удаления на 16 м. GLB профессора и морских жителей начинают загружаться при приближении к соответствующему берегу/озеру на 24 м; экземпляры скрываются на 30 м. Разница порогов предотвращает мигание. До подхода загружаются только координаты мест размещения, а экземпляры для непосещённых озёр не создаются. Общие GLB запрашиваются по одному разу и остаются в кэше; повторный подход использует прежние объекты, вдали анимации останавливаются. Если игрок ушёл во время загрузки, завершение запроса не показывает модель вдали или в белой комнате. `ready` у компонентов обозначает готовность координат; `site.loading` / `lake.loading` — загрузку экземпляров. Диагностика: `/proximity-checks.html`.

## Озёра и морские жители

В каждом из четырёх озёр находятся три анимированные рыбы-клоуна и один омар из предоставленных GLB-моделей. Рыбы плавают в толще воды, омар перемещается по дну. Вода прозрачнее, на дне добавлены камни и растения. Это учебная морская экспозиция с увеличенным масштабом животных: она не изображает их совместную естественную среду обитания в пресном озере. Для стилизованной модели омара выбран справочный профиль *Homarus americanus*.

Наведите курсор на животное, направьте на него прицел при управлении мышью/PS5 или луч VR-контроллера. Рядом с моделью появится временная 3D-карточка: опасность, место обитания, размер и масса, состояние популяции, питание и интересный факт. Карточка следует за животным и исчезает примерно через 1,1 секунды после отвода курсора/луча. Рельеф перекрывает выбор сквозь землю. Меню и переход в белую комнату скрывают карточки и морскую экспозицию; после возвращения на планету животные снова доступны. Наблюдать за ними можно без входа в аккаунт; их движение локальное, без серверной синхронизации.

Модели находятся в `public/assets/marine/`, лицензии и авторы — в [LICENSE.md](public/assets/marine/LICENSE.md). Каталог «модель + описание + параметры размещения» расположен в `public/client/marine-catalog.js`. Исходные GLB сохранены без изменений, включая скелеты, текстуры и анимации; геометрия и материалы разделяются между копиями, вдали от озера анимация приостанавливается.

Биологическая справка проверена 31.10.2026. Общая численность не подменяется оценкой охранного статуса; средние массы из исследования и исключительные размеры обозначены отдельно. Источники: [Oregon Coast Aquarium](https://aquarium.org/animals/ocellaris-clownfish/), [FishBase](https://www.fishbase.se/summary/Amphiprion-ocellaris), [Iwata et al., 2020, таблица 2](https://journal.bdfish.org/index.php/fisheries/article/download/JFish20179/144/), [Fisheries and Oceans Canada](https://www.dfo-mpo.gc.ca/species-especes/profiles-profils/american-lobster-homard-eng.html), [NOAA Fisheries — популяция и питание](https://www.fisheries.noaa.gov/species/american-lobster), [NOAA — клешни и внешний вид](https://www.fisheries.noaa.gov/species/american-lobster/recreational).

Проверка в браузере: откройте `/marine-checks.html`. Она загружает настоящую игру и проверяет обе GLB, анимации, размещение во всех озёрах, выбор мышью/прицелом/VR-лучом, время скрытия, перекрытие рельефом и отключение экспозиции в другом мире. VR-проверка использует синтетическую позу контроллера; проверка в физическом шлеме выполняется отдельно.

## Голосовой чат

После входа в общий мир нажмите **N · Микрофон выкл** в панели справа или клавишу **N**. Разрешите браузеру доступ к микрофону. Повторное нажатие останавливает захват и освобождает устройство. Микрофон изначально выключен, в том числе после переподключения. Слушать участников можно с выключенным микрофоном. Кнопка «Заглушить участников» отключает только входящие голоса; **M** управляет звуками природы. Если браузер запретил автоматическое воспроизведение, появится кнопка «Включить голоса участников».

В VR кнопка **X** левого контроллера переключает микрофон, состояние отображается в HUD. Разрешение на микрофон удобнее выдать до входа в VR. При выходе из аккаунта, отзыве сессии, потере WebSocket или закрытии страницы захват останавливается, аудиоэлементы и peer-соединения удаляются. Поздний ответ на запрос разрешения после выхода также освобождает устройство.

Используется существующий C++ backend: `/signal` проверяет сессию и пересылает SDP/ICE только участникам комнаты. В уже имеющихся peer WebRTC-соединениях заранее согласуется двусторонний аудиоканал; включение/выключение микрофона через `replaceTrack` не прерывает игровые DataChannels. Звук передаётся браузерным WebRTC (обычно Opus), до 8 участников, общая громкость без затухания по расстоянию. Сам C++ процесс звук не декодирует и не записывает: по умолчанию медиа проходит через встроенный локальный TURN в том же C++ процессе; при внешней RTC-конфигурации — напрямую либо через указанный TURN. C++ world-канал рыб остаётся отдельным.

### HTTPS и разные сети

Для микрофона нужен `localhost`/`127.0.0.1` либо HTTPS; обычный HTTP по LAN-адресу не подходит. Для доступа с других устройств поставьте HTTPS reverse proxy перед loopback-портом C++ сервера с поддержкой WebSocket `/signal`.

Без внешнего RTC-файла C++ автоматически запускает TURN из libjuice на случайном UDP-порту **127.0.0.1** и выдаёт авторизованным клиентам `iceTransportPolicy: "relay"`. Это устраняет зависимость локального чата от разрешения mDNS-адресов между Safari/WebKit и Chrome. Случайный пароль меняется при каждом запуске; relay ограничен loopback и 128 allocations. Он подходит только для браузеров на том же компьютере, что и backend. Для разных сетей/NAT задайте собственные STUN/TURN, создав файл **вне `public/`**, например `runtime/rtc.json`:

```json
{
  "iceServers": [
    { "urls": ["stun:turn.example.com:3478"] },
    {
      "urls": ["turn:turn.example.com:3478?transport=udp", "turns:turn.example.com:5349?transport=tcp"],
      "username": "REPLACE_WITH_TURN_USERNAME",
      "credential": "REPLACE_WITH_TURN_PASSWORD"
    }
  ],
  "iceTransportPolicy": "all"
}
```

Адреса и реквизиты в примере необходимо заменить на действующие. Запуск:

```bash
PLANET_RTC_CONFIG="$PWD/runtime/rtc.json" ./scripts/start.sh
# Или напрямую: ./build/planet_server --rtc-config=/absolute/path/rtc.json
```

C++ проверяет конфигурацию при старте и передаёт её только в авторизованном `welcome`. Ошибочный JSON, неизвестные схемы, TURN без реквизитов и `relay` без TURN останавливают запуск с ошибкой. `iceTransportPolicy: "relay"` принудительно направляет браузерные WebRTC-соединения через TURN. C++ world-канал также использует выданные STUN/TURN-кандидаты; libjuice поддерживает серверный TURN по UDP. При внешней RTC-конфигурации локальный relay отключается: ваш TURN должен быть доступен браузерам и C++ серверу по указанным портам. Статические TURN-реквизиты доступны вошедшим участникам: используйте ограниченную по правам и сроку учётную запись, не административный пароль. Ротация credentials внешнего TURN здесь не реализована; локальный relay получает новый пароль при запуске процесса.

### Проверка голоса

`./scripts/build.sh` собирает C++ сервер и выполняет четыре CTest-проверки, включая проверку RTC-конфигурации и авторизованной выдачи voice-настроек.

Для необязательного интеграционного теста нужны Node.js и Playwright (для работы приложения они не нужны):

```bash
npm install --prefix .cache/voice-tests --no-audit --no-fund playwright
.cache/voice-tests/node_modules/.bin/playwright install chromium
PLAYWRIGHT_MODULE="$PWD/.cache/voice-tests/node_modules/playwright" node scripts/voice-test.mjs
```

Можно использовать установленный Chrome, указав `CHROME_PATH` вместо загрузки Chromium. Тест использует встроенный TURN и обычную политику воспроизведения браузера, без отключения autoplay-ограничений и без предварительного разрешения микрофона в Chrome. Тест сам запускает отдельный C++ сервер со временной БД в памяти и три браузерных клиента с синтетическими микрофонами. Проверяет выбор relay-кандидатов в обоих направлениях, входящие RTP-пакеты, заметную энергию декодированного аудио и продвижение времени воспроизведения аудиоэлементов, поздний вход, выключение/включение микрофона, отключение входящего звука, разрыв и восстановление соединения, отказ и позднее разрешение на микрофон, остановку при отзыве сессии, а также работу world/DataChannels. В сетевой части рендеринг сцены заменён заглушкой; сетевой и аудиокод выполняется настоящий. В конце проверяется кнопка микрофона на полной странице с 3D-сценой. Проверка настоящих микрофонов, шлема и вашего TURN через интернет выполняется отдельно.

Для проверки совместимости Chrome ↔ WebKit:

```bash
.cache/voice-tests/node_modules/.bin/playwright install webkit
VOICE_WEBKIT=1 PLAYWRIGHT_MODULE="$PWD/.cache/voice-tests/node_modules/playwright" node scripts/voice-test.mjs
# Два отдельных процесса WebKit и третий участник Chrome:
VOICE_WEBKIT=all PLAYWRIGHT_MODULE="$PWD/.cache/voice-tests/node_modules/playwright" node scripts/voice-test.mjs
```

WebKit запускается отдельным процессом. В нём только `getUserMedia` заменён генератором тона (Playwright не умеет выдавать разрешение микрофона WebKit); SDP/ICE, Opus, TURN, приём и аудиоплеер выполняются движком. Это тест совместимости WebKit, а не проверка физического микрофона в установленном Safari. В Safari после начала захвата повторяется запуск входящего аудио; если браузер блокирует воспроизведение, нажмите «Включить голоса участников». При системной паузе микрофона статус сообщает об этом; при проверке двух вкладок Safari одна из них может потерять захват — используйте Safari + другой браузер или два устройства с внешним TURN.

Справка API: [replaceTrack](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpSender/replaceTrack), [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).
